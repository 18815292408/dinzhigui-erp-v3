# 方案与订单流程融合设计

## 问题诊断

当前系统存在两条割裂的平行工作流：

1. **订单流**（orders）：`待派单 → 待接单 → 设计中 → 待下单 → 待打款 → 待出货 → 安装中 → 已完结`
2. **设计方案流**（designs）：`草稿 → 已提交 → 已确认`（独立运行，不驱动订单状态）

这导致：
- 设计师有两个入口做方案（订单详情页 + 方案管理页），数据可能不一致
- 方案确认时会自动创建 installation，违反"安装管理独立"原则
- 老板看不到订单和方案的完整链路
- 前端显示的是老的设计方案流程线，而非统一的订单流程线

## 融合原则

**订单状态机是唯一流程引擎。设计方案不再是独立工作流，而是订单的一个"数据模块"。**

## 统一状态机

```
待派单 (pending_dispatch)
  ↓ 导购派单
待接单 (pending_design)
  ↓ 设计师接单（自动创建 design 记录，status=draft）
设计中 (designing)
  ↓ 设计师提交方案（design status → submitted）
待下单 (pending_order)
  ↓ 设计师下单到工厂
待打款 (pending_payment)
  ↓ 老板确认打款
待出货 (pending_shipment)
  ↓ 设计师填写出货时间 + 指派安装师傅（自动创建 installation 记录）
安装中 (in_install)
  ↓ 安装师傅在安装管理模块反馈进度
已完结 (completed)
```

## designs 表角色重定义

- **不再是独立工作流**，仅存储方案数据（标题、面积、描述、附件等）
- `status` 字段降级为标记：
  - `draft` = 设计中（订单处于 designing）
  - `submitted` = 方案已提交及之后（订单处于 pending_order 及以后）
  - **废弃 `confirmed` 状态**
- 必须有 `order_id`，创建时机 = 设计师接单时
- 编辑窗口 = 订单处于 `designing` 状态时

## installations 表角色重定义

- **完全独立在安装管理模块**，与方案确认解耦
- 创建时机 = 订单进入 `in_install` 时（即 set-shipment 接口）
- 关联 `order_id`（已有）+ `design_id`（已有）
- 进度更新在 `/installations` 管理，订单详情页只读展示

## 前端页面调整

### 订单详情页（/orders/[id]）—— 唯一流程展示页

按订单状态动态显示不同操作区：

| 订单状态 | 显示内容 |
|---------|---------|
| pending_dispatch | 派单操作 |
| pending_design | 等待设计师接单提示 |
| **designing** | **嵌入设计方案编辑表单**（设计师可编辑，其他人只读） |
| pending_order | 设计方案只读展示 + 下单至工厂操作 |
| pending_payment | 等待打款提示（老板视角显示确认打款按钮） |
| pending_shipment | 填写出货时间 + 指派安装师傅 |
| **in_install** | **显示关联安装单信息 + 安装进度只读展示** |
| completed | 完结归档信息 |

### 方案管理页（/designs）—— 改为"设计任务"视角

- 不再显示所有独立 design，而是显示当前设计师需要处理的设计任务
- 列表项展示：订单号、客户名、订单状态、设计修改时间
- 点击跳转 `/designs/[id]` 或 `/orders/[id]`

### 方案详情页（/designs/[id]）—— 订单上下文增强

- 顶部增加"订单流程上下文"卡片（显示当前订单状态、订单号）
- 中间展示设计方案数据
- 底部提供"返回订单详情"入口
- **移除"确认方案并创建安装单"按钮**（此操作已不存在）
- **移除状态回退按钮**（状态由订单驱动，设计层面不操作）

### 安装管理页（/installations）—— 保持独立

- 增强显示关联订单号
- 安装进度更新在此页面操作

## API 调整

### 新增/修改接口

1. `POST /api/orders/[id]/accept`
   - 现有：只更新订单状态
   - **新增**：自动创建 design 记录（`order_id=订单ID, status='draft'`）

2. `POST /api/orders/[id]/submit-design`
   - 现有：只更新订单状态
   - **新增**：同步更新关联 design 的 `status='submitted'`

3. `POST /api/orders/[id]/set-shipment`
   - 现有：更新订单状态 + 指派安装师傅
   - **新增**：自动创建 installation 记录（`order_id=订单ID, design_id=关联designID, status='pending'`）

4. `GET /api/orders/[id]`
   - **新增**：关联查询 design 信息（`designs(*)`）

5. `GET/POST /api/designs`
   - 查询时关联 `orders(order_no, status, customer_name)`
   - POST 时**必须传入 `order_id`**，不再允许自由创建

6. `GET/PUT /api/designs/[id]`
   - 查询时关联 `orders(*)`

## 数据迁移

现有 designs 数据中，部分已有 `order_id`（迁移脚本 005 已执行），部分可能为 null。

对于 `order_id` 为 null 的历史 design：
- 如果 title 格式为 `{客户名} - 设计方案`，尝试匹配 orders 表中的同名客户
- 匹配失败则保留为"历史遗留数据"，不在新流程中显示

## 废弃功能

- `/designs/new` 页面的自由创建方案功能（设计师必须从订单接入）
- 方案详情页的"确认方案并创建安装单"按钮
- 方案详情页的状态回退按钮
- designs 的 `confirmed` 状态语义
